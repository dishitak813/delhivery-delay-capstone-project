# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone project, AI and Machine Learning Certification Program, E&ICT Academy IIT Roorkee. All data is synthetic (made by `generate_data.py`). All work is on the `main` branch.

The repo answers three questions: how long will a parcel take (regression), which parcels will miss their promise (classification), and which hubs need which playbook (clustering). A final script turns 48 new parcels into an action list.

## How to run

Run these from the repository root of a fresh clone, in this order:

```
pip install -r requirements.txt
python generate_data.py          # prints 24 1224 48
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

`requirements.txt` pins pandas, numpy, scikit-learn and joblib with `==`. `models/delay_model.pkl` is regenerated by running `python package_model.py`. The committed pickle loads reliably only on the scikit-learn version pinned in `requirements.txt` (1.9.1). If your installed versions differ, re-run `python package_model.py` instead of loading the committed pickle. Running `predict_delay.py` twice gives byte-identical output.

## Data findings

Source files: `outputs/part_a_checks.csv`, `part_a_delay_by_group.csv`, `part_a_correlations.csv`.

1. **Service type.** Express is delayed most often: 119 of 243 parcels, a delay rate of 0.4897. Standard is 0.2056 and Economy is 0.0857. Express has the tightest promise (36 hours), so it has the least room for error.
2. **Hub tier.** Delay rate rises sharply with tier: Tier 1 is 0.0400, Tier 2 is 0.2150 and Tier 3 is 0.4400.
3. **Distance.** Delay rate grows fast with distance: 0.0219 for 0-200 km, 0.1368 for 201-400 km, 0.4364 for 401-600 km and 0.8523 for 601+ km. Almost every parcel travelling more than 600 km is late.
4. **Correlation with delivery_hours.** The three strongest columns by absolute correlation are promised_hours (0.8372), distance_km (0.4013) and n_stops (0.3247).
5. **Why log of declared value.** The filled declared_value_inr has a mean of 1533.0542 (INR 1,533.05) against a median of 1121.5 (INR 1,121.50), a long right tail. After the log transform the mean (7.0277) and median (7.0224) are almost equal, so the column is far less skewed.

Cleaning results: 1,224 raw rows, 24 duplicates removed, 1,200 rows kept, 5 sentinel weights (999) set to missing, 12 service-type spellings reduced to 3, and 0 missing values in the 17 features, `delivery_hours` and `is_delayed`. The overall delay rate is 0.2317 (278 delayed parcels).

## Model results (regression)

Source files: `part_b_metrics.csv`, `part_b_tree_depth.csv`, `part_b_gb_learning_rate.csv`, `part_b_cv.csv`, `part_b_checks.csv`.

- **Split and scaling.** Split sizes are 840 / 180 / 180. The scaler was fitted on training rows only: the scaled training means are about 0 while the scaled test rows have a max absolute column mean of 0.2187, which is expected because the test rows were not used to fit the scaler.
- **Baseline.** Predicting the training mean for every validation row gives R2 = -0.0212. It explains none of the variation in delivery time (slightly worse than just using the validation mean). Any real model must beat this.
- **Winner on validation.** Linear regression has the lowest validation RMSE: 4.8912 hours (R2 0.9313). Gradient boosting is very close at 4.9165 hours (R2 0.9306), then random forest at 5.4680 and the decision tree at 6.2796.
- **Tree depth.** Depth 1 is high bias: train RMSE 11.6334 and validation RMSE 12.1324 are both high (gap only 0.4990), and depths 2 and 3 are still too simple. The best depth is 6 (validation RMSE 6.2796). No depth limit is high variance: train RMSE 0.0 but validation RMSE 7.7890, a gap of 7.7890. Depth 12 shows the same trend (gap 6.0560).
- **Learning rate.** 0.1 is best (validation R2 0.9306). At 0.01 (R2 0.7127) the model is too slow: 100 trees with tiny steps have not learned enough. At 1.0 (R2 0.8440) each step is too large and overshoots, so the fit is noisy.
- **Cross-validation.** On the 1,020 training-plus-validation rows, gradient boosting has mean R2 0.9352 (std 0.0044) and linear regression 0.9261 (std 0.0048). So the CV ranking disagrees with the single validation split. I would ship **gradient boosting**: the CV uses five folds on 1,020 rows, so it is more reliable than one 180-row split where the two models differ by only 0.0253 hours of RMSE, and boosting can pick up interactions such as sale x Express and rain x long distance that a straight line cannot. The pre-set rule of the brief scores the lowest-validation-RMSE model (linear regression) once on the test rows: R2 0.9493, RMSE 4.5235 hours. That test result is for linear regression only; gradient boosting was not scored on test.

## Model results (classification)

Source files: `part_c_models.csv`, `part_c_feature_scores.csv`, `part_c_selectk.csv`, `part_c_tuning.csv`, `part_c_thresholds.csv`, `part_c_final_test.csv`, `part_c_final_config.csv`.

- **Split.** Stratified split 840 / 180 / 180 with 195 / 42 / 41 delayed parcels.
- **Blind baseline.** Predicting "not delayed" for everyone gets accuracy 0.7667 but catches 0 of the 42 delayed parcels (recall 0). It is useless because the whole point is to find the delayed ones. The trained models reach accuracy between 0.8833 and 0.9056 on validation, with F1 from 0.7470 (decision tree depth 6) to 0.8046 (logistic regression).
- **Noise columns.** The five bookkeeping columns together hold about 0.22 of the forest's importance, even though they carry no signal (a forest splits on them by chance). By F-score, all five are outside the top 7 (ranks 8, 12, 14, 16 and 17) and each has an F-score below 5. The top seven by F-score are distance_km, hub_tier, hub_daily_capacity, n_stops, promised_hours, rain_flag and sale_event_flag; the smallest of their F-scores is 36.7281.
- **SelectKBest table.** Validation F1 is 0.6988 for k=5, 0.8333 for k=7, 0.7857 for k=10, 0.8049 for k=12 and 0.7848 for k=17. k=7 is best: with 5 features we lose real signals (rain and sale), and adding more columns only adds noise.
- **Tuning.** Tuning did not beat the untuned forest on validation. Grid search got val F1 0.7750 (best CV accuracy 0.8952), randomized search 0.7848 (CV accuracy 0.8905), and the default forest on the same 7 columns got 0.8333. With only 42 delayed parcels in validation, one parcel changes F1 by roughly 0.02, so these differences are within noise; tuning on a 180-row validation set mostly fits luck. The final configuration is therefore the default forest on 7 features (`default_forest_same_7_features`).
- **Threshold.** The chosen alert threshold is 0.5, the highest threshold whose validation recall is at least 0.80. At 0.5 validation recall is 0.8333 and precision 0.7955. At 0.6 recall drops to 0.7619 (precision 0.8889), below the target. At 0.4 recall is 0.8810 but precision falls to 0.7400.
- **Test result (scored once).** Precision 0.6889, recall 0.7561, F1 0.7209, accuracy 0.8667 (TP 31, FP 14, FN 10, TN 125). Test recall is lower than validation recall (0.7561 against 0.8333), which is about 3 delayed parcels out of 41 and misses the 0.80 aim. With only 41 delayed parcels, this gap is plausible random variation, not proof that the model is broken. I did not retune after seeing it.

## Operations recommendation

- **Escalate hubs (9).** HUB13 Nagpur, HUB15 Kochi, HUB17 Patna, HUB18 Ranchi, HUB19 Guwahati, HUB20 Raipur, HUB21 Bhubaneswar, HUB23 Siliguri and HUB24 Agartala. The segment's mean delay rate is 0.4600 (mean delivery hours 64.6504, mean distance 470.4757 km). Standard (7 hubs) has delay rate 0.0257 and Watch (8 hubs) has 0.1550.
- **Tier label mismatches.** `tier_vs_segment_mismatch.csv` lists four hubs: HUB07 Kolkata (Tier 1 but Watch, delay rate 0.14), HUB13 Nagpur (Tier 2 but Escalate, 0.46), HUB15 Kochi (Tier 2 but Escalate, 0.36) and HUB22 Dehradun (Tier 3 but Watch, 0.20). So the tier label is a size and capacity label and should not be used to pick a playbook; use the segment from the hub's actual behaviour instead.
- **Alert threshold.** Flag a parcel when its delay probability is 0.5 or higher. On the test rows, about 7 of every 10 flagged parcels are really delayed (precision 0.6889) and about 7.6 of every 10 delayed parcels are caught (recall 0.7561).
- **New parcels.** Of the 48 new parcels, 8 are flagged and 6 of those need escalation to the hub manager (the other 2 get a proactive customer call).
- **Why K = 3.** The across-to-within ratio is 2.8940 for K=2, 5.3928 for K=3, 6.3047 for K=4 and 6.8866 for K=5. The ratio keeps rising, but K=4 gives cluster sizes 8-7-5-4 and K=5 gives 8-7-4-3-2, so they contain clusters of 4, 3 and 2 hubs, which are too small to carry their own playbook. K=3 gives 9-8-7, matches the three playbooks that operations runs, and the jump from K=2 to K=3 (2.5 points) is much bigger than from K=3 to K=4 (0.9 points).

## Production plan

**(a) Production-readiness map**

- Accuracy: `outputs/part_c_final_test.csv` and `part_b_metrics.csv` hold held-out test numbers.
- Reliability: `predict_delay.py` fills gaps with stored medians (`models/impute_values.csv`), so new parcels with missing values still get a score. The check on `new_shipments.csv` leaves 0 missing feature values.
- Reproducibility: pinned `requirements.txt`, `random_state=42` everywhere, and committed `generate_data.py`. `package_model.py` rebuilds the pickle.
- Performance (speed): a 100-tree forest on 7 selected columns, loaded once from the pickle. Scoring 48 parcels is one `predict_proba` call.
- Maintainability: one copy of the cleaning and feature code in `src/shipment_prep.py`, one script per part.
- Consistency: training scripts and `predict_delay.py` both call `clean_shipments` and `build_features`, and `models/feature_order.csv` fixes the column order.
- Monitorability: `outputs/` keeps baseline numbers (delay rate, flagged share, recall) to compare against.

**(b) What to monitor, and triggers**

1. Weekly delayed share of delivered parcels. The history shows 0.2317. Trigger: outside 0.15 to 0.32 for two weeks in a row.
2. Weekly share of parcels flagged. On validation the model flagged 44 of 180 (0.2444). Trigger: below 0.16 or above 0.33 for a week.
3. Recall on parcels whose outcome is now known (4-week rolling window, at least 40 delayed parcels). Validation recall was 0.8333 and test recall 0.7561. Trigger: below 0.65.
4. Missing-value rate for distance_km, parcel_weight_kg and declared value. Trigger: above 5% in a week (history is 36 of 1,200 for distance, 3.0%).

**(c) Retraining and the sale window.** Retrain monthly on the latest delivered parcels, and immediately if trigger 1 or 3 fires. Re-check the threshold each time on a fresh validation window. The 15-28 September sale window (`sale_event_flag`) adds delay (up to 12 extra hours for Express in the generator), so compare a sale week with a previous sale window, not with ordinary weeks, and do not treat a sale-week jump in delays as drift. Data drift here would look like a change in the distribution of distance_km or n_stops (for example new longer lanes), a hub whose behaviour changes so its segment changes, new service types, or a rising share of missing values.

## Limitations

1. The data is synthetic, made by a script with known rules. Real Delhivery data would be noisier and the scores here would likely be lower.
2. The test set has only 41 delayed parcels, so test precision and recall (0.6889 and 0.7561) have wide uncertainty.
3. The threshold and the model choice were tuned on a single validation split with 42 delayed parcels, so they could shift on a different split.
4. The history covers only 90 days (July to September 2026), so there is no yearly seasonality beyond the one sale window.
5. The hub segments rest on only 24 hubs with 50 parcels each, and the hub delay rates are noisy estimates.
6. The fill-in medians were computed on the full historical table before splitting. They carry no target information, but they are a small departure from strictly training-only fitting.
